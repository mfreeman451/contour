# Staging deployment

The application is deployed occasionally while development runs locally. All deployable application work targets **farm01 staging**. `overlays/prod` reserves **carverauto** configuration; there is no production Argo application or promotion automation.

## Prerequisites

- Farm01 must have a **supported CloudNativePG operator with PostgreSQL 18 support**. The inspected operator is **1.25.0**, which needs upgrading before this cluster can roll out. Manage that shared operator through the infrastructure/GitOps repository rather than installing a second operator here.
- cert-manager and Gateway API are required. The staging HTTPRoutes attach to `farm01-edge/farm01-gateway`, using its `http`/`https` listeners and shared wildcard certificate.
- Harbor must have the `contour` project and an image-pull account. Register farm01 in ArgoCD under destination name `farm01`, and ensure the Git source has a `staging` branch containing this change.
- Configure a Google Web OAuth client with callback **https://contour.k8s-farm.carverauto.dev/auth/google/callback**. Use a separate local callback/client as appropriate.

## Secrets

Create a private `.local/staging.env` containing `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `HARBOR_USERNAME`, and `HARBOR_PASSWORD`. An optional `DATABASE_PASSWORD` sets/rotates the database owner password. Run:

```sh
scripts/bootstrap-staging-secrets .local/staging.env
```

This explicitly applies to context **farm01**, namespace **contour-staging**. It generates cryptographic keys once and preserves existing keys/passwords on subsequent runs. Secret values travel through kubectl stdin, never command-line arguments. The private input is gitignored.

| Secret | Consumer |
| --- | --- |
| `contour-db-credentials` (`username`, `password`) | CNPG bootstrap/managed owner and application/migration database connection |
| `contour-web-secrets` | Web pods: Google ID/secret, exact callback, cookie encryption/signing key, Guardian signing key |
| `contour-cluster-secrets` (`RELEASE_COOKIE`) | Web/core ERTS distribution authentication |
| `contour-registry` | Private image pulls |
| `contour-db-ca` | Generated by CNPG; application verifies the database certificate and service hostname |
| `contour-distribution-tls` | Generated by cert-manager; mutual TLS for ERTS distribution |

Secrets are references in the manifests; credential values are not checked in. After rotating application keys or the database credential, restart the relevant deployments once CNPG has reconciled the managed role. Certificate rotation also requires restarting BEAM nodes to reload distribution certificates. The namespace-specific distribution CA and cookie must remain isolated between staging and production.

## Build and rollout

```sh
bazel build --config=rbe //:release
scripts/image registry.carverauto.dev/contour/contour:staging-COMMIT
# Push the built image through your configured Harbor credentials.
```

The image packages the already-built Bazel release and ERTS; it does not resolve dependencies or recompile application code. Current release/image targets are **Linux amd64**. Use the printed immutable registry digest after pushing:

```sh
cd k8s/overlays/staging
kustomize edit set image registry.carverauto.dev/contour/contour=registry.carverauto.dev/contour/contour@sha256:IMAGE_DIGEST
cd ../../..
kustomize build k8s/overlays/staging
```

Commit the staging image reference to the `staging` branch, then apply `k8s/argocd/staging.yaml` to the ArgoCD control cluster and sync **contour-staging**. Its destination is farm01. Sync is manual; the base deliberately contains `build-required` so an unbuilt foundation cannot accidentally deploy. No cluster changes are made by rendering or building.

Argo waves establish the namespace/service account/config/certificates, reconcile CNPG, run the migration Sync hook, and then roll out web/core deployments. CNPG must become healthy before the migration hook proceeds. The hook runs with `CONTOUR_ROLE=migrate`, without a web server, OIDC provider, or distributed node. Application-owned AshPostgres migrations and Oban migrations must succeed before deployments advance.

## Runtime topology

Both Deployments start with **three replicas**. Every pod advertises `contour@POD_IP`. libcluster resolves the shared headless `contour-discovery` service; discovery needs no Kubernetes API token or RBAC. Horde registry spans the runtime nodes, while only core nodes join the placement supervisor through `pg` role advertisements. CRDT sync interval/max size are explicit configuration. Active-game recovery semantics and match draining are subsequent alpha tasks.

Distribution uses mutual TLS on fixed port **9100**, with EPMD on **4369** and a secret cookie. The client verifies the certificate identity `contour`, independent of changing pod IPs. NetworkPolicy allows distribution between application pods, database connections to CNPG, web ingress from Envoy, DNS, and HTTPS egress for Google/provider metadata. Probes remain available to kubelet. Application pods run as uid 10001 with a read-only root filesystem, restricted capabilities, and no mounted service-account token.

Liveness is independent of database health (`/health/live`); readiness queries PostgreSQL (`/health/ready`). Web uses port 4000; core exposes an internal health listener on 4001. Public staging routes redirect `/health` to login. Each role has a disruption budget allowing one unavailable pod, zero-unavailable rolling updates, node spreading, and a 120-second termination grace period. CNPG uses three instances with required hostname anti-affinity and farm01's `local-path` storage.

Scale core independently with its Deployment replica count through GitOps. Each web/core pod has a **10-connection** pool; with three of each, app pools reserve 60 of PostgreSQL's 200 connections. Budget headroom for migrations, maintenance, operator activity, and failover before adding replicas or increasing pools. Storage on farm01's current local-path class does not support expansion; plan volume capacity deliberately. Backups/PITR and production promotion need an explicit storage/retention decision before production use.
